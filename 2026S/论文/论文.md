### 2.1. Rust Future 无栈协程

在现代操作系统与高性能网络编程中，协程（Coroutine）作为一种用户态的轻量级并发单元，因其上下文切换开销远低于操作系统线程而被广泛应用。根据实现方式的不同，协程主要分为有栈协程（Stackful Coroutine）与无栈协程（Stackless Coroutine）。Rust 语言在构建其异步编程模型时，基于“零成本抽象”（Zero-cost Abstraction）的设计哲学，最终确立了以 Future 特型（Trait）为核心的无栈协程机制。

#### 2.1.1 无栈状态机模型

与 Go 语言中的 Goroutine 等有栈协程不同，Rust 的无栈协程不会为每个并发任务分配独立的运行栈空间。在 Rust 中，使用 async 关键字修饰的函数或代码块，在编译期会被 Rust 编译器（rustc）自动转换为一个实现了 Future 特型的匿名状态机（State Machine）。

该状态机本质上是一个枚举（Enum）类型，其变体（Variant）对应了协程在各个 await 挂起点的状态，并负责保存跨越 await 点的所有局部变量。由于不依赖系统级的栈空间分配与切换，Rust 的无栈协程在创建和切换时的内存占用极小（通常仅需数十字节到数百字节），且生命周期完全由编译器静态推导和优化。这种极高的内存利用率和执行效率，使其非常适合应用于资源受限的嵌入式环境或对性能要求极高的操作系统内核级并发中。

#### 2.1.2 核心抽象：基于轮询的 Future Trait

Rust 异步生态的基础是标准库提供的 core::future::Future 特型。与 Node.js 等采用基于事件回调（Callback-based）的模型不同，Rust 采用了基于轮询（Polling）的驱动模型。Future 的核心定义如下：

```Rust
pub trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}
```

任何异步任务都必须实现该特型。poll 方法是推动异步任务执行的核心引擎：

Poll::Ready(Output)：当异步任务计算完成时，poll 会返回该状态，并携带最终的执行结果，此时状态机终止。

Poll::Pending：当异步任务由于等待 I/O 就绪或定时器未超时而无法继续执行时，poll 会返回该状态。此时，当前协程会非阻塞地主动让出（Yield） CPU 控制权，交还给上层的调度器（Executor）。

此外，poll 方法的接收者类型为 Pin<&mut Self>，这是 Rust 为了保证状态机自引用安全（Self-referential Safety）而引入的内存固定机制，确保了异步任务在内存中的地址不会在轮询期间发生移动，从而避免指针悬垂问题。

#### 2.1.3 唤醒机制与 Reactor-Executor 模型

由于 Future 的轮询是被动的，这就引发了一个核心问题：当 Future 返回 Poll::Pending 后，调度器应当在何时再次轮询该任务？为了避免无效的忙轮询（Busy Wait），Rust 引入了 Waker 唤醒机制。

在 poll 方法的参数中，Context 上下文对象封装了一个 Waker 实例。当底层的异步事件（例如本文后续章节将探讨的硬件定时器 Timer 触发或外设中断到来）就绪时，底层事件分发器（Reactor）会调用注册在其内部的 Waker::wake() 方法。该方法会将对应的任务标记为“就绪态”，并通知顶层的执行器（Executor）将该任务重新推入可执行队列中等待下一次 poll。

#### 2.1.4 异步运行时的解耦特性

值得注意的是，Rust 标准库仅提供了 Future 接口、编译器状态机生成以及基础的唤醒抽象，并未提供内置的异步运行时（Runtime）。这种极度的解耦设计虽然增加了初期的开发门槛，但赋予了开发者极大的灵活性。开发者可以根据具体的应用场景选择或定制执行器。

例如，在传统的用户态应用程序中，通常会使用 Tokio 或 async-std；而在本文重点探讨的裸机（No-std）与微控制器环境中，则需要引入为嵌入式定制的宏观异步执行器（如 embassy），或在内核层面自主研发底层的协程调度框架（如在 rCore 中实现特定的异步驱动模块）。这种语言层面的机制支持，正是本文后续实现操作系统级异步驱动模块的理论基石。

### 2.2. embassy 介绍

正如上一节所述，Rust 语言虽然在语法层面原生支持了无栈协程与 Future 特型，但将其应用于实际的工程开发时，仍需要一个具体的异步运行时（Runtime）来负责任务的调度与事件的轮询。在传统的操作系统级应用中，通常依赖 Tokio 等基于标准库（std）和堆内存分配的庞大运行时；然而，在操作系统内核（如 rCore）或微控制器（MCU）等缺乏底层 OS 支撑的“裸机（Bare-metal/no_std）”环境中，此类运行时无法运行。为此，Embassy 框架应运而生。

Embassy（Embedded Async）是 Rust 生态中目前最具代表性、专为嵌入式与裸机环境设计的现代化异步并发框架。它不仅提供了一个极致轻量级的异步执行器（Executor），还构建了一套基于异步机制的硬件抽象层（HAL）。

### 2.2.1 no_std 环境下的异步执行器设计

在没有操作系统线程调度的裸机环境中，实现并发的传统做法通常是引入实时操作系统（RTOS）以提供抢占式多任务，但这会带来显著的栈空间开销与上下文切换延迟。Embassy 充分利用了 Rust 的无栈协程特性，实现了一个无需依赖堆内存分配（Heapless）的静态执行器。

由于在嵌入式与内核环境中，内存的确定性（Determinism）至关重要，Embassy 的调度器要求所有的异步任务（Task）在编译期或初始化阶段完成静态分配。框架内部通过一种巧妙的静态生命周期管理机制，保证了任务的内存单元被长期固定（Pinned）在 .bss 或 .data 数据段中。这种设计彻底杜绝了运行时内存碎片化与内存耗尽（OOM）的风险，同时保证了极低的调度开销，使其非常适合作为底层操作系统的协程调度参考模型。

### 2.2.2 硬件中断驱动的 Reactor 唤醒模型

上一节提到，Rust 的异步模型依赖 Waker 进行任务的唤醒，而 Embassy 最核心的创新在于将底层硬件中断与 Rust 的异步 Waker 机制进行了无缝融合。

在 Embassy 的架构中，硬件设备（如定时器 Timer、串口 UART、DMA控制器等）充当了底层事件分发器（Reactor）的角色。其工作流如下：

任务挂起：当驱动程序发起一次异步 I/O 操作（例如设置一个延时定时器）时，驱动层会配置好底层硬件，并将当前上下文的 Waker 保存到全局或特定的外设上下文中，随后返回 Poll::Pending 让出 CPU。

中断触发：当硬件设备完成操作（如定时器触发超时中断）时，CPU 跳转至对应的硬件中断服务例程（ISR）。

唤醒调度：在 ISR 中，中断处理函数会提取出之前保存的 Waker 并调用其 wake() 方法，以此通知 Embassy 执行器该硬件事件已就绪。执行器随后会将对应的异步任务重新放入就绪队列，等待下一次主循环轮询。

这种基于中断的唤醒机制避免了 CPU 盲目的轮询查询（Busy-waiting），使得系统在空闲时可以进入低功耗睡眠模式（如 ARM 的 WFI 或 RISC-V 的 WFI 指令），从而极大地提升了裸机系统的 CPU 利用率和能效比。

### 2.2.3 异步硬件抽象层（Async HAL）与驱动生态

除了执行器，Embassy 还提供了一套完备的异步驱动生态。传统的嵌入式驱动在处理慢速外设时，往往需要使用阻塞延时或复杂的状态机来处理时序逻辑；而在 Embassy 提供的 Async HAL 中，开发者可以使用串行化的同步代码思维，配合 await 关键字来编写高并发的底层驱动程序。

例如，在实现一个复杂的传感器驱动时，可以直接使用 timer.await 等待时间间隔，或使用 dma_channel.read().await 等待总线数据传输完毕，而无需手动维护繁琐的中断回调函数。

### 2.2.4 Embassy 对本文研究的启示

Embassy 框架在裸机异步编程领域的成功实践，为本文后续设计 rCore 的异步驱动模块提供了重要的参考价值。Embassy 证明了：

纯静态的异步运行时不仅是可行的，而且在性能和内存安全上具有传统同步驱动无法比拟的优势。

硬件中断与 Waker 的结合是实现高效异步驱动程序的关键。
因此，本文在后续章节（即第 5 章）面向 rCore 操作系统内核设计异步驱动模块时，将充分吸收 Embassy 在无堆内存管理、中断事件映射以及 Timer 异步抽象等方面的核心设计理念，以构建符合微内核或宏内核架构需求的高效异步 I/O 子系统。

### 2.3. rCore 介绍

rCore 是由清华大学计算机系操作系统实验室（OS Lab）及 rcore-os 社区主导开发的一款基于 Rust 语言的现代化开源操作系统内核。作为传统 C 语言教学内核（如 uCore 和 xv6）的跨时代重构版本，rCore 的核心宗旨在于将 Rust 语言的系统级编程优势引入操作系统内核的开发与教学实践中。

#### 2.3.1. 基于 Rust 的内核安全性保障

传统操作系统内核通常采用 C/C++ 编写，极易引发空指针解引用、缓冲区溢出、内存泄漏以及并发场景下的数据竞争等内存安全问题。rCore 充分利用了 Rust 语言的核心特性来规避这些缺陷：

所有权与生命周期模型：rCore 在编译期通过严格的所有权机制管理内核对象的生命周期，实现了无需垃圾回收器（GC）的自动化内存管理，彻底消除了“释放后使用（Use-After-Free）”等隐患。

无畏并发（Fearless Concurrency）：借助于 Rust 的 Send 和 Sync 标记特型（Trait），rCore 在多任务与中断并发场景下，能够利用编译器在静态检查阶段拦截潜在的数据竞争问题，大幅提高了内核运行的稳定性。

#### 2.3.2. rCore 核心架构与子系统

标准的 rCore 主要基于 RISC-V 架构（通常为 RV64 指令集），并采用了经典的宏内核（Monolithic Kernel）设计。其核心组件高度模块化，主要包含以下几个关键子系统：

- 异常与中断处理（Trap Management）：利用 RISC-V 的特权级机制（Machine/Supervisor/User Mode），rCore 实现了完善的软硬件协同上下文保存与恢复机制，能够处理系统调用（Syscall）、时钟中断以及各类缺页异常。

- 内存管理（Memory Management）：基于 SV39 分页机制，rCore 实现了物理页帧分配器与虚拟内存空间（Address Space）的抽象，支持基于页表的细粒度内存隔离。

- 任务调度（Task Management）：rCore 实现了一套抢占式的任务调度框架，通过维护任务控制块（TCB）和就绪队列，配合硬件定时器中断（Timer Interrupt），实现了时间片轮转（Round-Robin）等多任务调度算法。

#### 2.3.3. rCore 的 I/O 模型与局限性

尽管 rCore 在内存安全与基础操作系统抽象上表现优异，但在其基础版本（如 rCore-Tutorial）中，设备驱动与 I/O 模型的实现相对简化的。这主要体现在：

同步阻塞调用：在处理诸如串口输入（UART）或块设备读取时，标准 rCore 多采用轮询等待（Busy-waiting）或简单的阻塞挂起机制。当设备未就绪时，当前任务会被直接阻塞，导致 CPU 资源的浪费。

缺乏统一的异步抽象：内核层面缺乏对底层硬件中断的高效分发机制，未能将 Rust 语言在用户态表现优异的 async/await 异步生态引入内核态。

这种传统的 I/O 处理方式在面对低速外设或教学演示时绰绰有余，但在面对需要高吞吐量、低延迟和高并发的外设通信时，就会成为系统的性能瓶颈。这也构成了本文在 rCore 基础上进一步探索与设计异步驱动模块的直接动机。通过引入无栈协程与异步执行器，可以从根本上重构内核与硬件外设的交互方式，实现真正非阻塞的内核 I/O 架构。

### 2.4. 关于 rCore-N

rCore-N 是在 rCore 第 5 章实验成果基础上进一步演化得到的一个研究型内核分支。与以教学为主要目标的标准 rCore-Tutorial 相比，rCore-N 在继承其基本地址空间、陷阱处理与任务调度框架的同时，对内核结构进行了面向研究需求的裁剪与扩展。一方面，它去除了部分与本文关注点关联较弱的教学性逻辑，例如不再区分完整的线程模型，而是仅保留进程模型；另一方面，也删减了标准 rCore 中基于 `Blocked` 状态和定时器唤醒队列的 `sys_sleep` 实现，使系统的等待与定时语义更多转向事件驱动和用户态自主管理的方向。这种“减法式重构”为后续引入异步驱动机制留下了更清晰的实验空间。

与标准 rCore 的另一项关键差异在于，rCore-N 针对用户态中断（User-level Interrupt）机制做了专门扩展。为了支持这一机制，rCore-N 不仅在内核中增加了用户态 Trap 管理、用户态定时器事件投递等相关逻辑，还依赖经过修改的 QEMU 运行环境，以模拟和支持用户态中断链路。借助这一能力，用户程序可以通过系统调用主动设置面向自身的定时事件，待事件到期后以内核转发的方式触发用户态中断处理流程。对于本文所研究的异步 timer 而言，这一机制非常重要，因为它意味着 Timer 不再只是内核内部的调度设施，而可以成为用户态与内核态之间共享的异步事件源。

在体系结构上，rCore-N 还从单核执行环境扩展为四核（4 hart）并行运行模型。系统启动后，4 个 hart 分别使用不同的 `boot_stack` 完成初始化，并运行各自的 idle 进程；但在调度层面，它们共享同一个全局 `ready_queue`。这一设计一方面提高了多核并发执行能力，另一方面也显著增加了共享数据结构访问时的同步复杂度。任一 hart 在访问 `ready_queue` 或其他共享内核对象时，都必须通过加锁保证互斥；而一旦这些锁出现在中断处理路径中，就会引入竞争、嵌套与死锁风险。正因如此，rCore-N 在定时器、睡眠和任务唤醒机制上的设计，与单核版本 rCore 呈现出明显不同的权衡逻辑。

此外，rCore-N 在设备驱动层面已经初步体现出“同步实现”与“异步实现”并存的设计思路。例如在串口逻辑中，系统同时提供了偏向传统阻塞/缓冲处理方式的 `BufferedSerial`，以及面向异步事件处理的 `AsyncSerial`。这说明 rCore-N 并非仅仅是在 rCore 基础上的功能删改，而是在逐步引入一种新的 I/O 抽象方向：即在保留必要同步接口的同时，探索以内核事件分发、定时器和异步任务协作为核心的驱动模型。对于本文而言，rCore-N 因而构成了一个比标准 rCore 更贴近研究目标的实验平台，既保留了操作系统内核的基本骨架，又具备多核、用户态中断和异步串口等特性，能够更真实地暴露异步 timer 在内核环境中面临的并发与调度问题。

## 3. timer 基本机制

时钟（Timer）机制是操作系统内核的“心跳”，不仅为系统提供时间基准，更是实现多任务抢占式调度、异步 I/O 超时控制以及低功耗睡眠等核心功能的基石。本章将从底层硬件时钟原理出发，对比分析传统 rCore 的同步时钟模型与 embassy 框架的异步事件驱动模型，为后续实现内核级异步时钟驱动提供理论依据。

### 3.1. timer 简介

在硬件层面，现代处理器通常配备了高精度的硬件定时器（Hardware Timer）。以 RISC-V 架构为例，其核心规范定义了 `mtime`（Machine Time）寄存器用于持续记录自系统启动以来的时钟周期数，以及 `mtimecmp`（Machine Time Compare）寄存器用于设置下一次时钟中断的触发阈值。当 `mtime` 的值增长到大于或等于 `mtimecmp` 时，处理器便会触发一次硬件时钟中断（Timer Interrupt）。

在操作系统软件层面，时钟机制的实现经历了从周期性滴答（Tick-based）**到**无滴答（Tickless / One-shot）的演进：

1. **周期性滴答模型**：内核以固定的频率（如 100Hz 或 1000Hz）设置 `mtimecmp`，触发周期性的时钟中断。这种方式实现简单，易于维护全局时间片，但在系统空闲或处理长延时任务时，频繁的无效中断会引发大量的上下文切换开销，导致 CPU 功耗增加。
2. **事件驱动的无滴答模型**：内核不再维持固定的中断周期，而是根据当前系统中距离超时最近的定时任务，动态计算并设置下一次的 `mtimecmp` 值。这种方式最大化了 CPU 的睡眠时间，是现代高性能异步操作系统的首选方案。

### 3.2. rCore timer 实现

基础版的 rCore（如 rCore-Tutorial）在设计上主要服务于教学，因此采用的是经典的**周期性滴答（Tick-based）模型**。

#### 3.2.1. rCore 底层时钟驱动与系统调用

在 rCore 中，时钟初始化主要依赖底层的 RustSBI 提供的接口。内核启动时，通过读取 RISC-V 的 `mtime` 寄存器获取当前时间，并加上一个固定的时间片长度（通常为 10ms 对应的时钟周期数），调用 `sbi_set_timer` 设置下一次中断。

每当发生时钟中断（Supervisor Timer Interrupt）时，内核会执行以下同步操作：

* 更新全局的 `TICKS` 计数器，维护系统运行时间。
* 触发任务调度器（Scheduler），检查当前任务的时间片是否耗尽。若耗尽，则强行挂起当前任务，将其移入就绪队列尾部，并切换至下一个任务。

#### 3.2.2. rCore 和 rCore-N 关于 timer 实现的差别

在 rCore-Tutorial-2025S 中，Timer 不仅承担内核时间片调度的职责，也参与了阻塞式休眠机制的实现。除周期性地通过 `set_next_trigger` 设置下一次时钟中断外，内核还维护了一套定时唤醒机制：当用户程序调用 `sys_sleep` 时，当前任务会被设置为 `TaskStatus::Blocked`，并通过 `add_timer` 注册到定时器等待队列中；当相应 Timer 到期后，内核在时钟中断处理路径中检查已到期的定时事件，将对应任务重新标记为就绪态并加入 `ready_queue`。因此，rCore-Tutorial-2025S 的睡眠语义本质上是“阻塞并等待内核唤醒”，而不是用户态主动轮询时间。

相比之下，rCore-N 在保留内核周期性调度时钟的基础上，引入了更细粒度的虚拟定时器（Virtual Timer）机制，将 Timer 的使用场景从“内核抢占”扩展到了“用户态定时事件”。其关键扩展体现在以下两个方面。

首先，rCore-N 仍保留了用于内核时间片轮转的 `set_next_trigger`，但其底层不再直接调用硬件定时器接口，而是进一步封装为 `set_virtual_timer(time, pid)`。其中，由内核调度器设置的周期性时钟中断统一记为 `pid = 0`，表示该类 Timer 属于内核自身，而非某个具体用户任务。这样一来，内核调度事件与用户定时事件便能够进入同一套定时管理框架。

其次，rCore-N 为每个 CPU 核维护了一个按照到期时间排序的定时器映射表，通常以 `BTreeMap<time, pid>` 的形式组织。每次插入新的定时事件时，系统都会检查该事件是否早于当前映射表中的最早到期项；只有当新事件成为“最近将要触发的事件”时，才会真正更新底层硬件 `mtimecmp`。这意味着 rCore-N 实际上采用了一种“按最近事件编程”的 One-shot 定时策略，而不是简单的固定周期重装。对于多个不同来源的定时请求，系统只需维护最早的一个硬件触发点，待其到期后再重新编程下一次中断。

在此基础上，rCore-N 进一步提供了 `sys_set_timer` 系统调用，使用户程序可以主动申请在未来某一时刻触发一个面向自身的定时事件。当该事件到期时，若当前正在运行的正是设置该定时器的任务，则内核可直接设置用户态时钟中断标志，使控制流转入用户态陷阱处理逻辑；若当前运行的是其他任务，则内核会先将该定时事件以 Trap Record 的形式写入目标任务的陷阱队列，待该任务再次获得调度时再行处理。由此可见，rCore-N 的 Timer 机制已经不再仅仅服务于“内核调度”，而是开始承担“异步事件投递”的职责。

从系统结构上看，rCore-Tutorial-2025S 与 rCore-N 在 Timer 设计上的差别，本质上反映了两种不同的时钟抽象层次：前者更强调“内核内部的阻塞唤醒”，即由内核维护休眠队列并在中断中直接完成任务解阻塞；后者则更强调“面向任务的定时事件投递”，将 Timer 从单纯的调度设施提升为可复用的事件源。虽然 rCore-N 的实现尚未形成完整的 Future/Waker 异步模型，但其“按最早事件触发中断”和“将到期事件投递给目标任务”的思路，已经在机制上接近后续 Embassy 式异步定时器所需的事件驱动框架。

#### 3.2.3. rCore-N 中 sleep 机制的局限性

需要指出的是，采用忙等式休眠机制的并不是 rCore-Tutorial-2025S，而是多核版本的 rCore-N。rCore-N 中的 `sleep` 更接近一种用户态循环等待：任务在尚未到达目标时间时持续检查时间条件，并通过反复让出处理器维持“等待”语义，而没有像 rCore-Tutorial-2025S 那样在内核中进入 `Blocked` 状态并等待定时器到期后被直接唤醒。

这种设计并非单纯出于实现简化，而是与 rCore-N 的多核调度结构密切相关。rCore-N 运行在多 hart 环境下，多个 hart 共享同一个 `ready_queue`，任何核心在访问该队列时都必须先获取相应的锁。如果在时钟中断处理路径中直接获取该锁，并尝试将某个休眠任务重新插入 `ready_queue`，就有可能与其他 hart 上正在进行的调度操作形成竞争，甚至诱发内核崩溃。出于避免中断上下文中复杂加锁的考虑，rCore-N 的原始实现并未采用“中断到期后立即解阻塞并入队”的方案，而是退回到了更保守的忙等式 sleep 设计。

然而，这种方式虽然规避了多核锁竞争带来的稳定性风险，却也带来了明显的效率问题。处于休眠阶段的任务并未真正退出调度体系，而是通过重复运行、检查时间、再次让出的方式消耗调度机会；当系统中同时存在大量 sleep 任务时，多个 hart 会频繁参与无效调度，导致处理器时间被浪费在不产生实际工作的轮询路径上。对于需要高并发、低延迟和低空转开销的异步 I/O 场景而言，这种 sleep 机制显然难以满足需求，这也构成了后续引入事件驱动异步 Timer 的直接动因。

### 3.3. embassy timer 实现

为了彻底解决内核态任务在延时等待时的阻塞与轮询问题，本文重点引入了 Rust 嵌入式生态中极具代表性的 `embassy-timer` 机制。与 rCore 的同步模型不同，Embassy 采用的是**纯事件驱动（Event-driven）与无栈协程（Future）深度绑定的抽象模型**。

#### 3.3.1. 基于 Future 的 `Timer` 抽象

在 Embassy 中，任何一次延时操作（如 `Timer::after(Duration::from_millis(100))`）都不会直接阻塞当前线程，而是会返回一个实现了 `Future` 特型的匿名状态机。
当执行器（Executor）首次 `poll` 该 Future 时，如果时间未到，它会执行两个核心操作：

1. 将当前协程的上下文唤醒器（`Waker`）注册到全局的定时器队列中。
2. 返回 `Poll::Pending`，主动让出 CPU 控制权，且**该任务在被主动唤醒前，绝不会被执行器再次轮询**。

#### 3.3.2. 静态定时器队列（Timer Queue）

Embassy 内部维护了一个纯静态的、无堆内存分配的定时器队列（通常实现为最小堆或时间轮）。该队列以各个注册任务的到期时间戳为排序依据。每次有新的 `Waker` 注册时，系统会自动计算当前距离最近的超时时间，并动态配置底层的硬件 Alarm（即动态更新 `mtimecmp`）。这就实现了极低功耗的 Tickless 机制。

#### 3.3.3. 中断驱动的 Waker 唤醒链路

Embassy 时钟机制的精髓在于**硬件中断与 Rust 异步原语的无缝结合**。当底层硬件时钟中断（Timer Interrupt）触发时，CPU 陷入中断服务例程（ISR）。ISR 的核心工作非常精简：
它仅负责从定时器队列中弹出所有已超时的节点，并依次调用这些节点绑定的 `waker.wake()` 方法。`wake()` 函数会通过底层的调度原语，将处于休眠态的异步任务重新推入 Executor 的就绪队列中。

通过这种架构，Embassy 彻底消除了 rCore 传统机制中的 Busy-waiting 和无效调度开销，实现了 O(1) 级别的时钟中断响应与协程唤醒。这一机制的先进性，为本文将 rCore 内核级时钟驱动重构为异步模型提供了完美的理论范式与参考实现。

## 4. rCore 实验

本章将详细阐述本课题实验环境的搭建过程及基础操作系统的实现。由于直接在裸机硬件上从零构建异步操作系统内核存在极大的工程难度，且容易偏离“异步驱动模块设计”的核心研究方向，本课题选择基于清华大学开源的操作系统教学项目（rCore-Tutorial）作为底层基座。在此基础上，通过系统性地完成基础内核实验，构建出一个完整的传统同步宏内核，为后续引入异步运行时与重构底层驱动提供可靠的验证平台。

### 4.1 rCore-2025S 课程实验

#### 4.1.1 简介

rCore-2025S 是基于 Rust 语言与 RISC-V 64 硬件架构的 2025 春季版操作系统内核实验框架。该框架摒弃了传统 C 语言内核中常见的内存不安全问题，充分利用 Rust 的所有权模型与严格的类型系统，实现了一个安全、模块化且可扩展的教学级宏内核。

在本课题中，rCore-2025S 扮演着双重角色：

1. **可靠的系统基座**：它提供了诸如物理页帧管理、SV39 多级页表、特权级上下文切换（Trap 上下文）等底层硬件抽象。这些基础设施与 I/O 模型的关联度较低，可以直接复用于本课题的异步内核架构中。
2. **反面对照组（Baseline）**：rCore-2025S 的原生架构是一个典型的同步阻塞系统。它依赖固定频率的硬件时钟滴答（Tick）进行任务抢占，并在处理外设 I/O 时采用盲轮询（Busy-waiting）机制。将其完整实现后，能够为本课题后续的异步化重构提供极其直观的性能对照与架构对比。

#### 4.1.2 rCore 实验完成过程

在开展核心的异步驱动重构之前，本课题首先沿着 rCore-2025S 的核心演进路线，从裸机启动开始，逐步实现了传统操作系统的四大核心子系统。这一过程不仅夯实了系统级编程基础，更暴露了同步阻塞模型在底层的局限性。具体完成的核心工作涵盖以下几个方面：

* **特权级机制与 Trap 异常处理**：
基于 RISC-V 的 M/S/U 特权级分离机制，实现了内核态与用户态的隔离。编写了汇编级别的 Trap  trampoline（跳板）代码，能够正确保存和恢复任务在陷入内核（软中断或系统调用）以及处理外部硬件中断时的寄存器上下文。这是所有内核态 I/O 操作的入口点。
* **物理与虚拟内存管理（SV39 分页架构）**：
实现了物理页帧的线段树分配器，并严格按照 RISC-V 的 SV39 虚拟内存规范，构建了三级页表映射机制（Page Table）。通过为内核与不同用户进程分配独立的地址空间（Address Space），实现了任务间的数据隔离。同时，该模块为后续异步执行器（Executor）在 `.bss` 数据段中静态分配无栈协程提供了内存连续性保障。
* **基于时钟滴答的进程管理与调度**：
实现了一套传统的时间片轮转（Round-Robin）调度器与进程控制块（PCB）。**在此阶段，系统严格依赖同步时钟模型**：内核初始化时配置硬件 `mtimecmp` 寄存器触发周期性的时钟中断（10ms/Tick）。每当 Tick 到来，内核便暂停当前任务并轮询就绪队列。这一实现过程让我深刻意识到，对于大量需要休眠等待（`sys_sleep`）的进程，传统内核只能依靠无休止的 `yield` 让出与重新唤醒来进行低效轮询，CPU 周期被大量浪费，从而直接印证了引入事件驱动与异步 Timer 的必要性。
* **文件系统与同步 I/O 接口**：
移植并完善了基于磁盘块设备的 `easy-fs` 文件系统，向上层用户空间提供了标准的 `read` 和 `write` 等系统调用。在实现串口通信（UART）与标准输入输出时，底层驱动采取了阻塞挂起的等待机制。

**阶段总结**：
通过完整贯穿 rCore-2025S 的各级实验，本课题成功构建了一个具备多道程序并发能力、内存隔离与基础 I/O 的同步版宏内核。这标志着基础平台搭建完毕，为第 5 章中剥离同步机制、引入 Embassy 异步运行时并重构底层的 Timer 驱动，扫清了体系结构上的障碍。

## 5. 异步驱动模块

### 5.1 异步 timer 设计与实现

本节面向 rCore-N 的多核内核环境，设计并实现一个参考 Embassy `timer` 思路、但又适配内核实际约束的异步定时器子模块。其目标并不是在内核中完整移植 Embassy 的执行时框架，而是在保留 rCore-N 现有 Trap 与调度结构的前提下，引入基于 `Future`/`Waker` 的定时等待机制，使定时事件能够以异步任务的方式被注册、挂起、唤醒和继续执行。

从模块划分上看，本文实现的异步 timer 主要位于 `os/src/async_timer` 目录下，由 `task`、`waker`、`queue`、`timer` 与 `time_driver` 五个部分组成。整体调用链可概括为：上层通过 `after_ticks` 或 `after_ms` 创建一个异步定时任务；该任务内部 `await` 一个 `Timer` Future；当 `Timer::poll` 发现尚未到期时，将当前任务对应的 `Waker` 注册到定时队列中并返回 `Poll::Pending`；当 S 态时钟中断到来时，`time_driver` 检查已到期定时事件并调用相应 `Waker` 完成唤醒；随后执行器在同一中断上下文中继续轮询已经变为就绪态的任务，直至执行其超时回调逻辑。

#### 5.1.1 基于 Future 的异步 timer 抽象

本文将定时器抽象实现为一个 `Timer` Future，其核心状态仅包含两个字段：到期时间 `expires_at` 与标记首次挂起行为的 `yielded_once`。其中，`expires_at` 表示该定时事件应当在何时被触发，`yielded_once` 则用于区分“首次注册等待”和“被唤醒后的再次轮询”两个阶段。

当执行器首次轮询 `Timer` 时，若当前时间尚未到达 `expires_at`，则 `Timer::poll` 会调用 `time_driver::schedule_wake(self.expires_at, cx.waker())` 将当前任务的唤醒器注册到定时队列中，并返回 `Poll::Pending`。当底层时钟推进至目标时间后，执行器再次轮询该 Future，此时若 `yielded_once` 已为真且当前时间满足超时条件，则返回 `Poll::Ready(())`，表示定时等待结束。这样，传统同步 `sleep` 所需的“阻塞线程”或“忙等轮询”被转换为了 Future 状态机上的一次挂起与一次恢复。

在接口层面，模块进一步向上封装了 `after_ticks`、`after_ms` 与 `add_timer` 等函数。其中 `after_ticks/after_ms` 负责生成一个异步任务，在 `Timer::after(...).await` 结束后执行给定回调；`add_timer` 则根据绝对时间戳与当前时间的差值，转换为相对延时后复用同一套异步机制。由此，内核中所有“未来某时刻执行某动作”的逻辑，都可以统一映射为“创建一个等待 Timer 的异步任务”。

#### 5.1.2 TaskRef、TaskHeader 与 Waker 的转换关系

为了让 `Waker` 能够在不依赖堆分配和复杂对象查找的前提下直接唤醒异步任务，本文在执行器内部设计了 `TaskHeader` 与 `TaskRef` 两级任务引用结构。`TaskHeader` 是异步任务的实际控制头，内部保存任务状态 `state` 以及被执行器轮询的 Future 对象；`TaskRef` 则是对 `TaskHeader` 裸指针的轻量封装，用作唤醒路径中的任务句柄。

具体而言，任务创建时先由 `TaskHeader::new` 分配一个 `Arc<TaskHeader>`，随后通过 `Arc::into_raw` 将其转化为原始指针，再由 `TaskRef::from_ptr` 封装为 `TaskRef`。反向地，当执行器需要真正访问任务内容时，再通过 `TaskHeader::from_ref(task_ref)` 将其重新还原为 `Arc<TaskHeader>`。这一组双向转换保证了异步任务在“可执行队列管理”和“Waker 唤醒路径”之间能够高效切换：执行器侧更适合持有 `Arc<TaskHeader>` 以进行队列管理与生命周期控制，而 `Waker` 侧则更适合仅持有一个可恢复到任务头的轻量原始句柄。

在 `Waker` 的实现中，本文没有为每次唤醒额外构造独立的闭包对象，而是直接以 `TaskHeader` 指针作为 `RawWaker` 的数据字段。`from_task(task_ref)` 会基于该指针构造出一个 `Waker`；当底层调用 `wake()` 时，`RawWaker` 的 `wake` 回调会将该指针重新解释为 `TaskRef`，并进一步调用 `wake_task(task_ref)`。后者执行的核心操作是将任务状态原子地改写为 `Ready`，从而使该任务在下一轮执行器扫描时重新变为可运行状态。也就是说，`Waker` 并不直接执行任务，而只是完成“将 Future 对应任务重新标记为可轮询”的状态跃迁。

这种设计与 Embassy 中“任务头指针 + 原始唤醒器”的基本思路是一致的，但实现上更贴合本文的内核环境：`TaskRef` 充当了 `Waker` 和执行器之间的最小连接件，`TaskHeader` 则承担真正的任务状态与 Future 存储职责。二者之间的相互转换，是整个异步 timer 子模块能够运转的关键基础。

#### 5.1.3 定时队列与 Time Driver 设计

在定时事件管理方面，本文借鉴了 Embassy `timer queue` 的核心思想，为每个 hart 维护独立的 `TimerDriver`。每个 `TimerDriver` 内部包含一个 `Queue` 以及一个记录当前硬件告警时间的 `AlarmState`。其中，`Queue` 负责保存一组尚未到期的 `(at, waker)` 项；`AlarmState` 记录当前已经写入底层 SBI `set_timer` 的最近到期时间。

需要特别说明的是，本文虽然引入了 Embassy 中“定时队列统一管理待唤醒任务”的设计思想，但并没有直接采用 Embassy 将 timer queue 实现为侵入式链表（intrusive linked list）、并把链表节点直接嵌入 `TaskHeader` 的做法。Embassy 之所以采用这种结构，是为了在嵌入式 `no_std` 场景中尽可能避免额外动态分配，并将任务控制块与定时等待节点紧密绑定。本文的实现环境则是 rCore-N 内核，目标首先是验证异步 timer 机制在操作系统中的可行性与执行语义，因此在工程实现上选择了更直接的方案：额外动态分配一个 `Vec` 作为 timer queue 的存储容器，将到期时间与对应 `Waker` 显式保存在队列项中。

当 `Timer::poll` 调用 `schedule_wake(at, waker)` 时，驱动首先将该 `Waker` 及其对应到期时间登记到队列中。如果新加入的任务使得“最近到期时间”发生变化，则驱动重新设置底层硬件时钟中断；否则沿用已有的硬件告警即可。这样做的结果是，系统始终只为“当前最近的一次超时事件”编程一次真实硬件中断，从而形成一种典型的 One-shot 定时策略。

与将链表节点内嵌进 `TaskHeader` 的方案相比，本文这种基于 `Vec` 的独立队列实现虽然会引入一定的动态内存分配开销，也不具备 Embassy 侵入式结构那样紧凑的内存布局，但其优点在于实现简单、调试直观，并且避免了为了适配链表节点而重构现有任务头结构。对于本文当前阶段以机制验证和原型实现为主的研究目标而言，这一权衡是可以接受的；而若后续继续向更高性能、更低分配开销的方向优化，则可以进一步考虑将 timer queue 改造为更接近 Embassy 的侵入式结构。

当 S 态时钟中断到来时，`time_driver::on_interrupt()` 会检查当前硬件告警是否已经到期。若到期，则调用 `next_expiration(now)` 依次弹出所有超时节点，并对每个节点保存的 `Waker` 执行 `wake()`。这些 `wake()` 调用并不会立即运行 Future，而只是把对应任务状态原子地更新为 `Ready`。在完成所有已到期事件的唤醒后，驱动继续计算下一次最近到期时间，并重新编程下一轮硬件定时器。至此，硬件时钟中断与软件 Future 唤醒之间的桥梁就被建立起来了。

#### 5.1.4 执行器与 Waker 统一放入 S Timer 中断上下文

本文实现与 Embassy 的一个关键差异在于：没有直接照搬 Embassy 的中断模式执行器，也没有采用其偏线程化的执行模式，而是将 `Waker` 触发与执行器 `poll` 统一放在同一个 S 态时钟中断上下文中完成。具体地，`async_timer_interrupt_handler()` 在进入 S Timer Trap 后，依次执行 `on_timer_interrupt()`、`executor_poll()` 与 `handle_os_tick()` 三个阶段，即先处理到期定时事件并唤醒任务，再在当前 Trap 上下文中继续轮询所有就绪异步任务，最后再处理与操作系统时间片相关的调度逻辑。

采用这种设计的原因，在于 rCore-N 的执行器不仅承担纯粹的 Future 推进职责，还可能在超时回调链路中间接触发操作系统调度路径。例如，模块中通过 `start_os_tick()` 与 `next_trigger()` 将“OS 时间片到期”也包装成一个异步定时任务；当该任务超时后，并不会在回调中直接切换上下文，而是仅设置 `PENDING_OS_TICK` 标志，待 `executor_poll()` 完成后，再由 `handle_os_tick()` 调用 `suspend_current_and_run_next()` 执行真正的任务切换。

这里必须强调 `suspend_current_and_run_next()` 的调用上下文要求。该函数本质上属于操作系统时钟中断处理路径的一部分，其执行依赖于当前 Trap 上下文保存的是由 S Timer 中断建立起来的内核现场。如果模仿部分执行器设计，将 Future 的轮询工作挪到一个专属的 S 软件中断（Supervisor Software Interrupt）中进行，那么 `suspend_current_and_run_next()` 一旦在该执行器上下文中被调用，就会面对与标准 S Timer Trap 不一致的上下文语义，进而导致任务切换现场不匹配，甚至破坏原有的内核调度流程。换言之，OS 时间片对应的任务切换逻辑不能脱离 S Timer 中断上下文独立运行。

因此，本文选择将“中断到期唤醒”和“执行器轮询推进”合并到同一个 S Timer Trap 中统一处理。这样做有两方面好处：其一，避免了在不同中断类型之间来回切换执行器上下文，降低了设计复杂度；其二，保证凡是可能进一步触发 `suspend_current_and_run_next()` 的异步定时回调，都运行在与 OS 时钟中断完全一致的上下文中，从而保持调度语义与现场切换逻辑的正确性。与此同时，通过 `PENDING_OS_TICK` 将“设置下一次 Tick”和“真正发起任务切换”延后到 `executor_poll()` 结束之后，也避免了在执行器正在遍历任务队列时直接切换上下文所带来的重入与一致性问题。

#### 5.1.5 小结

综上，本文实现的异步 timer 虽然借鉴了 Embassy 在 `Timer Future`、定时队列和 `Waker` 机制上的核心思想，但并未机械照搬其现成执行器模型，而是针对 rCore-N 的多核内核环境与 S Timer Trap 调度语义进行了有针对性的重构。其核心特征可以概括为三点：一是以 `TaskHeader`、`TaskRef` 和原始 `Waker` 组成轻量任务唤醒链路；二是以每 hart 一个 `TimerDriver` 的方式实现 One-shot 定时事件管理；三是将 `wake` 与 `poll` 统一收敛到 S 态时钟中断上下文中执行，以保证内核调度路径的上下文一致性。该设计为后续验证 Rust Future 的无栈特性以及评估多核环境下异步 sleep 的响应行为提供了基础实现支撑。

#### 5.2.1 Rust Future 无栈协程验证

在理论层面，Rust `Future` 之所以被称为“无栈协程”，关键并不在于协程执行过程中完全不使用栈，而在于它**不拥有独立于调用者之外的专用运行栈**。Future 的 `poll` 本质上仍然是一个普通函数调用：当执行器调用某个顶层 Future 的 `poll` 时，若该 Future 内部继续 `poll` 其所依赖的子 Future，就会在当前执行上下文的栈上形成一条普通的函数调用链。因此，协程执行期间所使用的栈，并不是像线程那样预先分配给任务本身，而是复用了当前调用 `poll` 的执行现场。

对于本文实现的异步 timer 而言，这一点体现得尤为明显。执行器在 S 态时钟中断上下文中调用任务的顶层 `poll`；若该任务内部又 `await` 一个 `Timer` Future，则会进一步进入 `Timer::poll`。此时，从执行器到顶层任务，再到叶子 `Timer` Future，会在当前 Trap 对应的内核栈上形成一条逐层嵌套的 `poll` 调用链。换言之，异步任务运行时所使用的栈空间，始终是触发本次轮询的那一条内核控制流所持有的栈，而不是 Future 自身单独拥有的栈。

更重要的是，当最内层的叶子 Future `poll` 返回 `Poll::Pending` 时，这一“挂起”语义并不会停留在某个中间栈帧内部，而是会沿着整条调用链逐层向上返回。也就是说，叶子 Future 返回 `Poll::Pending` 后，其父 Future 的 `poll` 会结束返回，再上一层 `poll` 也会继续结束返回，直到最终返回给执行器。随着这条返回链完成，先前为各层 `poll` 调用临时建立的中间栈帧都会被依次弹出，栈指针 `sp` 最终回退到执行器发起本轮 `poll` 调用之后的位置。

这正是“无栈协程”在运行时行为上的核心特征：Future 在挂起时并不会像线程那样保留一段独立栈空间来保存调用现场，而是仅将继续执行所需的状态保存在状态机对象本身中；一旦返回 `Poll::Pending`，调用栈便会完全退回，等待下一次由执行器重新进入 `poll`。从这一角度看，Rust Future 保存的是“状态”，而不是“栈”。本文后续的实验验证工作，将围绕这一点展开，即观察多次 `poll` 之间调用栈是否真正回收到执行器附近的固定位置，从而为无栈协程的堆栈复用特性提供实证支持。
